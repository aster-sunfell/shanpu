负载校准

仅用于人工选择负载，不计算方案收益。

负载校准：只测基线路径的三个预设档位，不计算方案收益。

基线 RPS输入有效响应 p99 ms网络/超时/内部错误非预期响应池等待次数候选

建议负载：暂无合适候选。规则：选择输入有效、无非预期响应、p99 在 300–1000ms 且有数据库等待或积压的最低档位。人工审查后在源码中冻结负载，再发起新的 measurement；不会自动采用建议，也不读取历史结果。

服务质量目标：响应 p99 ≤ 500 ms，完成 p99 ≤ 5,000 ms，分类错误比例 ≤ 0.001。

按时成功率以所有有效购买请求为分母，同时要求响应成功且满足响应期限、订单满足完成期限。百分比指标差值用百分点表示。SQL/事务尝试只用于解释机制。每轮 p99 单独计算；不把多个 p99 平均成总体分位数。业务 SQL 来自 mapper 计数，事务尝试不等于提交。Kafka 的 PENDING 仅为受理；完成量以提交证据为准。突发指标只计算突发段请求。

方法与适用范围

同一 runner 内交替配对，记录机器型号、镜像、配额和源码。GitHub Actions 每次机器性能可能不同，跨运行的绝对 RPS 与延迟不可直接归因于代码变化。固定负载只回答此条件下的收益，不推断最大容量。发压有效性、业务一致性与服务质量分别判定。原始数据见 performance-evidence artifact；每点 result.json、timeline.csv 和请求/提交证据可追溯。

闪铺 · GitHub Actions 单机受限资源测量vCPU 配额不等同于独占物理核或线上容量。
