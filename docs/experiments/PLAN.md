# 秒杀性能测量计划

本计划只回答三个问题：同压下快多少、满足同一 SLO 的容量高多少、同一波突发多按时完成多少订单。保留 A/B、B/C 两组，不生成 A/B/C 总排名。

## 1. 比较对象和资源

| 路径 | 行为 | 成功响应 |
|---|---|---|
| A | DB 事务同步扣库存、积分并创建订单 | PAID |
| B | Redis 过滤后执行相同 DB 同步事务 | PAID |
| C | Redis 预扣、Kafka ack 后受理，消费者执行 DB 事务 | PENDING |

待测端固定 2 核 / 2 GiB 预算：backend 0.8 核 / 512 MiB、MySQL 0.5 核 / 384 MiB、Redis 0.1 核 / 96 MiB、Kafka 0.6 核 / 448 MiB，系统和 Docker 预留 608 MiB。服务不能借用其他服务的空闲 CPU quota，结果限定在这套配额与持久化配置下。

发压端始终独立为另一个 Compose 项目，额外占用 1 核 / 512 MiB。正式测量支持两种部署模式：

- `--deployment same-host`：本机受限资源性能实验。所有待测服务绑定同一组两个逻辑 CPU，发压端绑定另一 CPU，三个 CPU 必须来自系统报告的不同物理核；保留现有各服务 CPU quota。绑定配置通过 `sut.sh pin` 自动选择或显式指定，持久化在忽略目录，启动前检查 Compose 和 Docker 实际配置。仍共享磁盘、缓存、内核和宿主机调度，结果不能直接外推独立 2 核 2 GiB 机器。
- `--deployment separate-host`：分机测量，正式运行的默认值。主机身份摘要必须不同，需确认独占负载与时钟同步。

两种模式都要求 Docker Engine 使用执行脚本所在 Linux 主机的内核；远程 Engine 和内核不同的 Docker Desktop Engine 不受支持，以免主机保护与真实宿主不一致。本机 WSL2 模式还需 PowerShell interop 可读 Windows 内存；虚拟 CPU 拓扑不代表 Windows 层物理核独占。引擎资源能力与实际配额启动前核验，不支持则停止。

2 核 / 2 GiB 指待测端预算，发压端、系统及其他程序需要额外资源。先停止无关开发服务；构建与测量分开。本机启动待测端、正式发压前，Linux 和 Windows（WSL 时）可用内存各至少 3 GiB。宿主机监控覆盖准备、发压、排空与分析，任一侧低于 1 GiB 即锁定本轮失败；低于 512 MiB 时优先停止本轮 runner 和同机专属待测容器，保留卷与现场，不影响无关容器。

## 2. 删除与保留

删除独立的 A/B 全有效、纯售罄和演示过滤次数的压测场景，移除旧 `--workloads`、`--calibrate` 和手填 `--q` 入口。旧冒烟数字从正式文档移除，私有历史证据归档，不用于性能结论。

保留单元测试、启动检查、提交证据、库存/积分/订单核对。这些只决定测量是否有效，不作为独立实验成果。开发期短时/单轮 `--validation-only` 结果仅进入忽略目录；本机性能实验不使用该开关。本机与分机模式遵守相同 SLO 和样本门槛。验证结果不生成提升比例，不能成为正式突发基线。

## 3. A/B：固定混合流量下的延迟和容量

固定 10% 新用户有效请求、90% 已购用户重复请求；这是可复现的实验条件，不代表线上比例。重复用户预先具备合法订单和积分流水，正式请求每人一次；库存与积分覆盖所有有效请求，不切换为售罄场景。

先对 A/B 使用相同输入 RPS 阶梯，再对有有效通过/失败上界的区间做中点细化，默认最多四轮。某条链路取得样本充分的有效失败上界后，不再对该链路继续升压；另一条链路可继续找边界。每点新活动、新用户，按轮次交错 A/B 顺序。两组均沿用相同预热规则：每点额外用户完成一笔订单、确认空闲，再保存 before 快照；预热订单不计入测量。该规则不是长期充分预热的保证，报告限定于该条件。

| 问题 | 主指标 |
|---|---|
| 同压下快多少 | 双方都通过 SLO 时，有效请求响应 p99 的配对差（毫秒及百分比），报告各轮中位数和范围 |
| 容量高多少 | 同一 SLO 下最高已证实通过输入 RPS、有效订单完成/s，以及失败上界 |
| 为什么有差异 | DB 事务尝试、mapper 调用、锁等待、连接池等待、JVM CPU/GC、目标机器资源曲线 |

有效请求与重复拒绝分别计算延迟和错误率。事务减少量只解释性能变化，不能换算成吞吐提升比例。容量结果限定为该固定混合流量下的承载能力。

## 4. B/C：稳定完成容量和突发业务收益

`capacity` 阶段使用库存、积分充足的独立新用户，分别寻找 B/C 稳定容量。B 的基线只从已完成的 v2 正式 `capacity.json` 读取，必须有有效通过/失败区间，区间宽度不超过通过档位的 10%（最低允许 1 RPS）。Q_B 取已证实通过档位，保留区间误差。

`burst` 阶段对 B/C 使用同一个 Q_B：0.5Q_B 低负载后，切换到 2Q_B 或 5Q_B 持续 5～10 秒，停止注入并观察排空。基线的 SLO、镜像、资源配额、实例及运行配置必须与当前环境一致。基线还绑定部署模式、两端主机身份和环境指纹、CPU 集合/拓扑、runner 镜像、VU、超时与排空配置；本机基线只能用于环境匹配的本机突发。缺少部署信息的旧报告必须重测。

同时输出：

- 在响应期限内多受理多少：B 为 PAID，C 为 PENDING，明确语义。
- 每个请求发起后，在完成期限内多完成多少 PAID 订单，作为主要业务收益。
- 最终完成量、完成延迟、未完成数、受理后待完成峰值、Kafka lag、排空时间和资源成本。

C 响应更快但按时完成未增加时，只能说明受理或缓冲收益；不能称为最终完成容量增长。响应失败但实际提交的订单独立记录。

## 5. SLO、样本和稳定性

默认响应 p99 ≤500 ms、最终完成 p99 ≤5000 ms、各流量类别错误率 ≤0.1%。这些是预先固定的实验假设，不能在结果出来后修改。两个方案使用相同要求。

正式容量点每段至少 60 秒、至少三轮；临界点按需要延长至 180～300 秒。每档位每条链路累计至少 1000 个有效请求响应样本，才参与容量和延迟提升结论。工具按有效流量比例与重复次数自动延长低速档窗口，最高 600 秒；仍不足时增加重复轮次或调整阶梯重跑。

稳态容量必须满足每轮分类 SLO、有效请求最终全部完成、无持续积压增长。工具报告有效请求累计到达减提交的 outstanding 曲线：末四分之一与首四分之一均值增长不得超过 max(2 单, 有效输入/s ×0.25 秒)，后半窗口线性斜率不得超过 max(0.05 单/s, 有效输入/s ×0.005)。这是带噪声容限的有限窗口判据，不是无限时间稳定性证明；临界点需延长观察。

数据错误、缺失提交证据、OOM、服务重启、配置变化和未排空使测量失效。未达到计划请求数、注入相对计划的 p99 延迟超过 100 ms、提前发出超过 50 ms 或 k6 异常归类为发压无效，不构成服务容量失败上界。样本不足也不构成失败上界。通过/失败不单调时不生成容量提升结论。

只测到通过点时写“至少 X RPS”；有上下界时报告区间，并注明提升数字来自已测档位。禁止把固定输入下的吞吐当成最大容量。

## 6. 有界数据处理与现场

用户分批创建、校验和写会话，凭证文件只保存连续 ID 段和固定签发时间，k6 在请求前计算 JWT，不复制完整 Token 数组。数据准备中的 SQL 和 Redis pipeline 每批最多 500 条。

请求、提交和快照写 JSONL；MySQL 使用流式游标，Redis 集合使用 SSCAN；离线关联、校验和精确分位数在 SQLite 上完成，缓存限制 8 MiB，排序临时数据落盘。k6 0.50 以 `--no-summary --no-thresholds` 关闭内存内指标汇总，分位数统一从磁盘逐笔证据计算；缺失注入通过计划数量与实际开始记录核对。

不再按总请求数设置 20000/100000 上限；进程、CPU、内存、磁盘剩余空间、VU 和时长仍受限制。

Redis 48 MiB 数据上限仍可能限制单点可准备的用户/会话数量。准备失败不输出容量结论，不通过增大目标预算绕过。每点完成、排空、核对且证据保存后，释放该点临时会话和 Redis 热缓存，避免历史测量点挤占下一点内存；DB 业务行和磁盘证据保留。失败或未排空点不释放现场。出现网络/超时/内部错误时完整观察到排空截止；C 中仍无明确提交去向的请求保留为不确定异步结果并停止后续点，不把它们作为容量失败上界。测量中时钟回跳或两机时钟分离也使该点失效，本机模式不放宽时钟检查。DB 数据仍累积，结果应记录本次准备规模并使用独占测试库。

宿主机独立看门狗每秒检查，Windows 内存和目标容器状态约每五秒检查，记录可用内存、换页计数、CPU/磁盘、容器状态及可读的 cgroup v2 资源计数；无 cgroup v2 计数时记录缺失，不假装已采集 RSS。观测和 PowerShell 查询有超时，采样并非实时硬保证。状态丢失或超过 30 秒未更新也停止发压。发压过程中触发时向 k6 发送 SIGINT，最多等待请求超时加 5 秒，再强制终止，并尝试有界排空、收集证据；本点 invalid，整轮 failed，不能作为容量上界或突发基线。准备阶段触发时在分批边界停止；主机看门狗不依赖容器内 SQL/API 返回。超过排空窗口、请求超时再加 30 秒仍未退出时，由宿主机停止 runner。内存临界保护优先于排空。证据盘可用空间至少 1 GiB。

显式 cleanup 先检查整轮归属，再按用户批次删除已关闭的专属 DB 数据。失败/未完成运行不允许自动清理。

## 7. 执行顺序与交付

先执行 CPU 绑定与本机预检（分机模式使用对应环境检查），确认稳定时钟、配额和余量；短窗口 validation 预跑只用于检查注入能力与选择初始阶梯，不作为性能结论。然后跑 A/B 容量阶梯及细化，随后跑 B/C 容量阶梯及细化，最后引用正式 B 基线执行突发。发压端受限或注入无效时停止后续阶梯，先修正发压工具，不推断目标容量。

两种部署模式的正式报告均进入 `docs/experiments/<计划>/<运行编号>/`，标题明确本机或分机；开发验证仍单独归档。交付两组性能报告，含部署模式、CPU 绑定/拓扑、虚拟化环境、运行条件、实际输入、分组延迟/错误率、每档位状态、容量区间、有效配对、按时受理/完成差值、积压与资源曲线，以及逐笔核对证据。操作见 [README.md](README.md)。
