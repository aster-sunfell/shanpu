# 秒杀压测重构计划

代码、报告和运行状态的目录约定及当前实现范围见 [实验说明](README.md)。

本文定义两组独立实验：A/B 验证 Redis 前置过滤的收益，B/C 验证 Kafka 异步受理的收益。两组分别准备数据、执行和出具报告，不再生成 A/B/C 总对比表。

本文是实验设计和验收依据。执行工具已按两组计划实现，入口、参数及产物见 [README.md](README.md)。低负载冒烟用于验证流程，不作为正式性能结果。文中的压力倍数和时长是初始建议，需根据试跑校准。

## 1. 链路定义与实验边界

| 场景 | 链路 | 接口成功状态 |
|---|---|---|
| A：DB 同步 | DB 扣活动库存、扣积分、写订单及积分流水，在同一事务内提交 | `PAID` |
| B：Redis + DB 同步 | Redis Lua 校验库存、去重及预扣，通过后执行 DB 事务 | `PAID` |
| C：Redis + Kafka | Redis Lua 预扣，等待 Kafka ack 后响应，消费者异步提交 DB 事务 | `PENDING` |

当前 A/B 共用 `SeckillOrderWriter.createSyncPaidOrder`，B 的成功订单仍然需要扣减 DB 活动库存，热点行锁仍然存在。因此不能预设 Redis 会显著提高全部有效请求下的订单吞吐，其主要收益假设是过滤重复和售罄请求。

当前 C 的消费者同样扣减 DB 活动库存。Kafka 的主要收益假设是提高短时受理能力、减少前台等待；最终完成容量仍受 DB 事务和消费能力制约。当前三个消费线程会竞争同一活动库存行，不能根据分区数推断完成吞吐的增长。

B 在两组实验中分别运行，作为各自的基线。两组的流量构成和统计目的不同，不交叉使用结果计算提升比例。

## 2. 实验一：A/B，Redis 前置过滤

### 2.1 实验目标

量化 Redis 对无效请求的过滤能力、对 DB 的减负效果，以及对有效下单延迟的保护作用，同时测量有效请求路径增加的开销。

### 2.2 流量档位

以下档位属于同一 A/B 计划，分别准备数据并运行，不在一轮测量中混合。

| 档位 | 初始状态及请求构成 | 主要问题 |
|---|---|---|
| 全部有效 | 库存和积分充足，全部为未购买用户，每人请求一次 | 正常下单增加多少 Redis 开销，容量和延迟如何变化 |
| 重复抢购 | 库存充足，90% 请求来自已购用户，10% 来自未购用户 | DB 操作减少多少，有效订单是否受到保护 |
| 已售罄 | 测量开始前库存为零，大量用户发起请求 | 售罄拒绝的处理能力与 DB 减负效果 |

重复抢购档位需提前准备合法已购状态：A 的 DB 中存在已购订单，B 的 DB 和 Redis 已购集合保持一致。准备订单、积分扣减、库存扣减保持业务一致，准备阶段不纳入测量；正式开始时，两侧剩余库存、用户构成等条件一致。正式新增订单与准备订单分别统计。

按固定比例交错安排请求，避免先发完重复请求再发有效请求。控制每用户请求频率，避免当前抢购接口每用户每秒 5 次的限流成为主要拒绝来源；429 单独统计。

### 2.3 施压方式

采用固定到达率，逐级增加输入 RPS。每个档位给 A/B 相同的请求速率、用户构成、持续时间和请求顺序分布。

先低压试跑，再增加到成功请求延迟明显恶化、内部错误或超时增加，或压测端实际发送量无法跟上。正式点可先运行 60 秒，接近容量上限的点延长至 3～5 分钟。

全部有效和重复抢购档位需准备足够的用户和库存，保证测量期间不会意外转为重复或售罄测试。若状态发生变化，该轮不能继续按原档位解释。

### 2.4 指标与结果解释

| 指标 | 用途 |
|---|---|
| 输入 RPS、实际请求 RPS、未发出的迭代数 | 确认输入压力及压测端是否受限 |
| 新增 `PAID` 订单/秒、成功请求 p95/p99 | 判断有效下单能力与延迟 |
| 重复、售罄请求的处理速率及 p95/p99 | 判断无效请求处理能力 |
| DB 事务数、SQL 执行数、锁等待、连接池等待 | 解释减负与瓶颈位置 |
| 超时、网络失败、内部异常、429 | 区分系统故障、限流与预期业务拒绝 |

只在相同档位、相同输入 RPS 下计算 A/B 收益。例如：90% 重复请求、输入 1000 RPS 时，DB 事务减少比例和有效订单 p99 变化。

容量比较必须使用相同的延迟与异常率要求，要求在正式运行前确定。允许出现全部有效时 B 收益不明显或略慢、重复与售罄时收益明显的结果。

## 3. 实验二：B/C，Kafka 异步受理

### 3.1 实验目标与输入条件

量化 Kafka 对平稳流量和短时突发的承接能力，同时测量最终订单完成速度、等待时间、积压和资源成本。

仅使用库存和积分充足的有效请求，独立用户每人请求一次。重复和售罄请求会被 B/C 共同的 Redis 层过滤，不作为本组主测流量。

### 3.2 统一结果口径

分别记录以下时刻：

1. 请求发起时间。
2. 接口响应时间：B 返回 `PAID`，C 返回 `PENDING`。
3. DB 事务实际提交完成时间：订单成为 `PAID`。

接口响应延迟需明确标注状态，C 的 `PENDING` 数量称为受理数，不能称为已完成订单数。最终完成数和请求发起至 DB 提交的延迟使用统一口径。

同步响应失败或超时的请求也需按关联信息核对最终订单，识别“响应失败但实际已提交”等情况，避免仅按响应统计业务结果。

### 3.3 压力过程

先在本计划中测出 B 满足约定延迟与异常率要求的稳定完成容量，记作 Q 单/秒，再执行以下过程。各压力点独立运行。

| 过程 | 初始建议 | 观察重点 |
|---|---|---|
| 平稳流量 | 约 `0.5Q`、`0.8Q`、`1.2Q` | 低负载额外成本、接近饱和后的排队与积压 |
| 突发流量 | 低负载 → `2Q～5Q` 持续 5～10 秒 → 停止发请求并等待完成 | 承接量、响应延迟、完成延迟、积压峰值及排空时间 |

B/C 接收相同规模、相同时间分布的请求。用户池与库存覆盖整个过程，避免有限库存掩盖积压增长。平稳过载点需要足够长的观察窗口，判断积压是否持续增长。

为排空设置明确的观察截止时间；截止时仍未完成的订单记为未完成，不能从完成延迟统计中静默排除。未完成请求及延迟样本覆盖率与分位数一起报告。

### 3.4 指标与结果解释

| 指标 | 用途 |
|---|---|
| 请求总数、受理数、最终完成数、失败及未完成数 | 完整解释整批请求的结果 |
| 接口响应 p95/p99 | 比较前台等待，标明 `PAID` / `PENDING` |
| 请求发起至 DB 提交的 p95/p99 | 比较用户获得最终结果的时间 |
| 每秒受理量、每秒完成量曲线 | 区分入口能力与最终处理能力 |
| 待完成订单峰值、Kafka lag 曲线、排空时间 | 量化缓冲能力和排队成本 |
| B 的连接池等待及超时；C 的重试、DLQ | 解释两条链路过载后的行为 |
| DB、Redis、Kafka、JVM 和宿主机资源 | 量化资源成本及资源争用 |

Kafka lag 归零不代表订单全部成功，必须结合受理订单逐笔核对、DLQ 和最终 DB 结果确认。Kafka offset lag 与业务待完成订单数分别报告。

接口很快但积压持续增长，只能证明短时缓冲能力，不能视为稳定完成容量提升。结论应同时说明同一波突发多接住多少订单、多久完成，以及增加多少资源和等待时间。

端到端时间采集使用业务事件的事务 `AFTER_COMMIT` 监听器和独立提交日志，业务层不直接依赖实验实现；时钟与采集误差见 README。现有数据库秒级时间字段不足以支持毫秒级分位数分析。测量不能通过在发压迭代内同步轮询来限制请求注入速度；若另行使用抽样轮询，应单独标明它测量的是用户可见完成时间和轮询误差。

## 4. 公共执行约束

- 固定活动业务参数、Caffeine 状态、JVM、Tomcat、连接池、日志级别、数据库持久化配置和资源配额；记录代码版本与实际配置。
- B/C 保留各自链路必需的异步幂等等操作，结果解释为当前整条方案的差异；消费并发固定并记录，不在不同压力点临时调优。
- 沿用直连后端 API 的入口，两组保持入口一致。监控 k6 和宿主机，识别压测端限制及同机资源争用。
- 使用独立用户预热代码和连接；正式开始前重置业务状态并确认缓存、库存和数据一致。用户池按到达率和总时长准备，禁止取模复用导致流量档位变化。
- 记录、固定后台任务的运行策略。性能测量期间避免自动补偿掩盖原始失败，原始结果与补偿后的结果分别保留。
- 每个正式压力点至少重复三轮，交错运行对照链路，报告中位数与波动范围。
- 每轮开始前确认上一轮在途请求、Kafka 消息及补偿任务已结束或已隔离；完成证据采集前禁止清理数据。
- 核对库存守恒、一人一单、用户积分及流水一致性；C 额外逐笔核对受理订单的最终去向。

## 5. 压测代码重构范围

以下工具重构已实现；正式性能结论仍需执行实验并审阅报告后确定。

1. 删除 A/B/C 总对比表、跨链路统一“成功 RPS”和写死的瓶颈结论。
2. 将旧 A/B/C 入口脚本替换为 A/B、B/C 两个计划入口，共用鉴权、请求、指标和数据准备工具。
3. 删除本轮不涉及的 D 缓存对比入口及编排。
4. 修正 RPS 固定除以 30、分位数缺失填零、网络失败漏计等问题，显式配置需要输出的分位数。
5. 将重复、售罄、限流、网络失败、超时和内部异常分别统计；保留原始结果和运行参数。
6. 增加请求与订单的关联及事务提交时间采集，支持完成曲线、端到端延迟和未完成订单核对。
7. 重构数据重置及清理流程，等待在途消息和一致性核对结束后再恢复数据。
8. 删除文档中预设的性能数字，改为链接到对应实验的实测报告。
