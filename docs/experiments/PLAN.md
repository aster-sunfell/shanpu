# 秒杀性能测量计划

本计划只回答三个问题：同压下快多少、满足同一 SLO 的容量高多少、同一波突发多按时完成多少订单。保留 A/B、B/C 两组，不生成 A/B/C 总排名。

## 1. 比较对象和资源

| 路径 | 行为 | 成功响应 |
|---|---|---|
| A | DB 事务同步扣库存、积分并创建订单 | PAID |
| B | Redis 过滤后执行相同 DB 同步事务 | PAID |
| C | Redis 预扣、Kafka ack 后受理，消费者执行 DB 事务 | PENDING |

待测端固定 2 核 / 2 GiB 预算：backend 0.8 核 / 512 MiB、MySQL 0.5 核 / 384 MiB、Redis 0.1 核 / 96 MiB、Kafka 0.6 核 / 448 MiB，系统和 Docker 预留 608 MiB。服务不能借用其他服务的空闲 CPU quota，结果限定在这套配额与持久化配置下。

MySQL 固定 8.0.46，保留 InnoDB 缓冲池 128 MiB、日志缓冲 8 MiB、32 连接及原刷盘策略。针对 384 MiB 配额关闭 Performance Schema，线程缓存固定 4；TempTable 全局内存限额 16 MiB、单表及 MEMORY 表上限 4 MiB、关闭 TempTable mmap 回退，超额内部临时表使用磁盘。SHOW GLOBAL STATUS 计数、应用提交日志和业务数据核对继续保留。这属于被测环境配置变化，A/B、B/C 均采用同一配置，实际变量记录在 mysql-settings.json、HTML 与基线指纹中；旧配置结果不能直接拼接比较，也不能作为当前突发基线。上述设置不构成 MySQL 总内存的数学硬上限，仍以容器配额、OOM 判定和实测为准。

发压端为另一个 Compose 项目，额外占用 1 vCPU / 512 MiB。唯一执行环境为 GitHub 托管 Linux Actions runner，部署标识 `github-actions`，报告协议 v3。每次运行自动分配互斥的两个被测端 vCPU 和一个发压端 vCPU，至少保留一个额外逻辑 CPU。优先将 SMT 兄弟放在同组，记录系统报告的拓扑；虚拟 CPU 和容器配额不代表物理核独占。

容器仍共享磁盘、缓存、内核及宿主调度，性能数字限于该 runner 环境和资源配置。当前至少需要 4 个可用 vCPU；不足时拒绝运行，不降低目标预算。构建与测量分开，容器启动和每阶段执行前核验 Docker 实际配额、CPU 集合及源码。可用内存至少 3 GiB；低于 1 GiB 停止注入，低于 512 MiB 优先停止本轮专属容器。

## 2. 删除与保留

删除独立的 A/B 全有效、纯售罄和演示过滤次数的压测场景，移除旧 `--workloads`、`--calibrate` 和手填 `--q` 入口。旧冒烟数字从正式文档移除，私有历史证据归档，不用于性能结论。

保留单元测试、启动检查、提交证据、库存/积分/订单核对。这些只决定测量是否有效，不作为独立实验成果。Actions 短时 smoke 的结果单独标记为 validation，正式实验不使用该标识。所有正式测量遵守相同 SLO 和样本门槛。验证结果不生成提升比例，不能成为正式突发基线。

## 3. A/B：固定混合流量下的延迟和容量

固定 10% 新用户有效请求、90% 已购用户重复请求；这是可复现的实验条件，不代表线上比例。重复用户预先具备合法订单和积分流水，正式请求每人一次；库存与积分覆盖所有有效请求，不切换为售罄场景。

先对 A/B 使用相同输入 RPS 阶梯，再对有有效通过/失败上界的区间做中点细化，默认最多四轮。某条链路取得样本充分的有效失败上界后，不再对该链路继续升压；另一条链路可继续找边界。每点新活动、新用户，按轮次交错 A/B 顺序。两组均沿用相同预热规则：每点额外用户完成一笔订单、确认空闲，再保存 before 快照；预热订单不计入测量。该规则不是长期充分预热的保证，报告限定于该条件。

| 问题 | 主指标 |
|---|---|
| 同压下快多少 | 双方都通过 SLO 时，有效请求响应 p99 的配对差（毫秒及百分比），报告各轮中位数和范围 |
| 容量高多少 | 同一 SLO 下最高已证实通过输入 RPS、有效订单完成/s，以及失败上界 |
| 为什么有差异 | DB 事务尝试、mapper 调用、锁等待、连接池等待、JVM CPU/GC、目标机器资源曲线 |

有效请求与重复拒绝分别计算延迟和错误率。事务减少量只解释性能变化，不能换算成吞吐提升比例。容量结果限定为该固定混合流量下的承载能力。

## 4. B/C：稳定完成容量和突发业务收益

`capacity` 阶段使用库存、积分充足的独立新用户，分别寻找 B/C 稳定容量。B 的基线只从已完成的 v3 正式 `capacity.json` 读取，必须有有效通过/失败区间，区间宽度不超过通过档位的 10%（最低允许 1 RPS）。Q_B 取已证实通过档位，保留区间误差。

`burst` 阶段对 B/C 使用同一个 Q_B：0.5Q_B 低负载后，切换到 2Q_B 或 5Q_B 持续 5～10 秒，停止注入并观察排空。基线的 SLO、镜像、资源配额、实例及运行配置必须与当前环境一致。基线绑定 Actions run、attempt、job、实例和环境指纹、CPU 集合/拓扑、镜像、VU、超时与排空配置。容量和突发在同一 job、同一服务环境中执行；旧环境或旧报告协议必须重测。

同时输出：

- 在响应期限内多受理多少：B 为 PAID，C 为 PENDING，明确语义。
- 每个请求发起后，在完成期限内多完成多少 PAID 订单，作为主要业务收益。
- 最终完成量、完成延迟、未完成数、受理后待完成峰值、Kafka lag、排空时间和资源成本。

C 响应更快但按时完成未增加时，只能说明受理或缓冲收益；不能称为最终完成容量增长。响应失败但实际提交的订单独立记录。

## 5. SLO、样本和稳定性

默认响应 p99 ≤500 ms、最终完成 p99 ≤5000 ms、各流量类别错误率 ≤0.1%。这些是预先固定的实验假设，不能在结果出来后修改。两个方案使用相同要求。

正式容量点每段至少 60 秒、至少三轮；临界点按需要延长至 180～300 秒。每档位每条链路累计至少 1000 个有效请求响应样本，才参与容量和延迟提升结论。工具按有效流量比例与重复次数自动延长低速档窗口，最高 600 秒；仍不足时增加重复轮次或调整阶梯重跑。

稳态容量必须满足每轮分类 SLO、有效请求最终全部完成、无持续积压增长。工具报告有效请求累计到达减提交的 outstanding 曲线：末四分之一与首四分之一均值增长不得超过 max(2 单, 有效输入/s ×0.25 秒)，后半窗口线性斜率不得超过 max(0.05 单/s, 有效输入/s ×0.005)。这是带噪声容限的有限窗口判据，不是无限时间稳定性证明；临界点需延长观察。

数据错误、缺失提交证据、OOM、服务重启、配置变化和未排空使测量失效。未达到计划请求数、注入相对计划的 p99 延迟超过 100 ms、提前发出超过 50 ms 或 k6 异常归类为发压无效，不构成服务容量失败上界。样本不足也不构成失败上界。通过/失败不单调时不生成容量提升结论。

只测到通过点时写“至少 X RPS”；有上下界时报告区间，并注明提升数字来自已测档位。禁止把固定输入下的吞吐当成最大容量。

## 6. 有界数据处理与现场

用户分批创建、校验和写会话，凭证文件只保存连续 ID 段和固定签发时间，k6 在请求前计算 JWT，不复制完整 Token 数组。用户及会话准备每批最多 500 条。重复用户的订单和积分流水按已验证的本批 ID 直接写入，造数事务每批最多覆盖 100 个用户，不关联历史订单表生成流水；事务内核对影响行数，失败时停止，不自动重放。保留原流量比例、预热规则及数据核对要求。

请求、提交和快照写 JSONL；MySQL 使用流式游标，Redis 集合使用 SSCAN；离线关联、校验和精确分位数在 SQLite 上完成，缓存限制 8 MiB，排序临时数据落盘。k6 0.50 以 `--no-summary --no-thresholds` 关闭内存内指标汇总，分位数统一从磁盘逐笔证据计算；缺失注入通过计划数量与实际开始记录核对，同时将 k6 的 Insufficient VUs 警告作为独立丢失到达证据，防止边界额外迭代掩盖缺失。每个到达率场景默认预分配并固定 100 个 VU，CPU/内存配额不变；VU 用尽仍中止测量，不降低有效性要求。

不再按总请求数设置 20000/100000 上限；进程、CPU、内存、磁盘剩余空间、VU 和时长仍受限制。

Redis 48 MiB 数据上限仍可能限制单点可准备的用户/会话数量。准备失败不输出容量结论，不通过增大目标预算绕过。每点完成、排空、核对且证据保存后，释放该点临时会话和 Redis 热缓存，避免历史测量点挤占下一点内存；DB 业务行和磁盘证据保留。失败或未排空点不释放现场。出现网络/超时/内部错误时完整观察到排空截止；C 中仍无明确提交去向的请求保留为不确定异步结果并停止后续点，不把它们作为容量失败上界。测量中时钟回跳或两机时钟分离也使该点失效，Actions 模式保留时钟异常检查。DB 数据仍累积，结果应记录本次准备规模并使用独占测试库。

宿主机独立看门狗每秒检查 Linux 可用内存、换页、CPU、磁盘和单调时钟，约五秒检查容器状态、重启和可读的 cgroup v2 计数。状态丢失或超过 30 秒未更新时停止发压。触发保护先向 k6 发送 SIGINT，进行有界排空并保存证据，随后强制停止。测量标为无效，不能用于容量上界或突发基线。

每阶段保留原始证据并归档。每次 Actions 使用全新数据库、凭证及数据卷，归档结束后销毁专属环境，不提供跨运行的人工数据清理入口。内部截止时间为测量停止和证据上传预留余量，平台强制终止仍可能阻止收尾。

## 7. 执行顺序与交付

Actions 先检查环境、构建镜像、启动并核验服务，随后在同一 runner 进行真实预检：按初始容量阶梯预计请求量的 1.2 倍快速造数、核对混合数据，并对 A/B/C 各执行最高初始 RPS 的 3 秒请求。MySQL 工作集估算余量需在启动时至少 64 MiB、预检运行时至少 32 MiB；计数不可用、OOM、重启、造数或请求核对失败时停止。该余量策略属于运行准入检查，不改变正式 SLO，也不保证可分配内存或长期稳定。

预检通过后归档证据，销毁专属容器和数据卷并复用镜像重建；验证业务表、Redis 和提交日志清空，以及新实例的镜像和配额与预检一致。正式执行要求本次任务、代码、参数和新环境匹配的一次性预检记录，随后才执行 A/B 容量、B/C 容量及引用本次合格 B 基线的突发。预检标记 validation，不输出容量结论，不作为突发基线；初始阶梯之外的细化、突发及长时间效应仍由正式实验判断。具体步骤和预算见 [README.md](README.md)。短时 smoke 仅用于流程验证。发压受限、数据错误、证据缺失或未排空时停止后续实验，不推断服务容量。

结构化结果、逐笔证据、资源采样和服务日志作为 Actions artifacts 保存。每次均生成可离线打开的 HTML；验证和失败报告明确标记。通过 Actions 页的 Run workflow 按钮选择 main 手动启动完整正式实验，结束后自动发布 Pages 报告网站；push 不触发压测。历史索引保留最近 30 次及最近一次完整正式实验。源码分支不存放运行数据。操作见 [README.md](README.md)。
