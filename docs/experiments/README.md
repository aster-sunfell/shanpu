# Redis 过滤与 Kafka 削峰实验

在 GitHub Actions 的 **Performance experiments → Run workflow** 中选择一个实验。每个 run 只启动所选实验，独立生成证据和 HTML 报告；正式实验不由 push 触发；相关代码变更只触发独立工具回归。需要两个实验时分别发起两个 run。

| 实验 | 对照 | 固定流量 | 重复 | 主指标 |
|---|---|---|---|---|
| `redis-filtering` | A 数据库同步 / B Redis 过滤后同步 | 600 RPS，60 秒；90% 已购重复、10% 有效购买 | 每路径 3 次，AB / BA / AB | 有效购买响应 p95/p99、按时成功率、最终完成率及错误率 |
| `kafka-burst` | B Redis 同步 / C Kafka 异步 | 100 RPS × 20 秒 → 600 RPS × 10 秒 → 100 RPS × 30 秒；全部有效购买 | 每路径 3 次，BC / CB / BC | 全程下单事务开始速率峰值、事务并发峰值；订单完成分位数、最终完成率与积压代价 |

两项实验的正式注入时间均为 6 分钟。另有镜像构建、当前机器生成器校验、环境启动核验、每路径固定 90 秒热身、数据准备和排空。排空最长 120 秒，确认无待完成订单、无 Kafka lag、无活跃事务后提前结束。不能保证整个 workflow 6 分钟结束。

工作流只选择实验，不再提供 calibration，也不进行容量搜索或读取历史来选择负载。Redis 固定 600 RPS，Kafka 固定 600 RPS 突发段，在同一个 run 内完成三轮交替对照。修改负载需要提交配置并新建 run，不能与旧配置合并计算收益。

每条路径固定热身三块：100 RPS × 30 秒、200 RPS × 30 秒、200 RPS × 30 秒，顺序同样交替。短窗口 p95 和 CPU 波动仅作诊断，不决定是否延长热身或取消测量。前两块出现已知发压不足或响应失败时，仅在订单、积分、库存与提交证据核对通过且确认排空后继续。任一路径最后一块输入无效或响应异常，则标记 inconclusive，不开始正式对照。数据不一致、未完成订单或未知执行错误仍立即中止。

## 环境与公平性

本地开发依赖容器按需启动，前后端可手动启动。生产和压测待测端完整容器化并共享业务配置与资源设置，服务 `unless-stopped`；发压任务 `restart: no`。六个待测服务绑定同一组两个逻辑 CPU，取消服务级 CPU 配额和权重调整，空闲 CPU 时间可供其他服务使用；后端 JVM 可见处理器为 2。内存上限仍分别为 backend 512、MySQL 384、Redis 96、Kafka 384、frontend 192、Nginx 64 MiB，共 1632 MiB，另计宿主预算 416 MiB（不是硬预留）。发压端另配 2 vCPU / 2 GiB，固定 6400 VU，不动态扩池。启动和观测时验证 Docker 设置以及实际 cgroup 的 cpu.max / cpuset.cpus.effective。

两个端绑定同一 GitHub-hosted VM 的不同 CPU 集合，按拓扑避免跨端使用同一物理核的 SMT 线程；仍共享磁盘、缓存、内核与宿主机。两个逻辑 CPU 不保证等于两个物理核，cpuset 也不代表独占或宿主保留。GitHub Actions 每次分配的 CPU 型号、宿主争用可能变化。因此收益用**本次 run 内同负载的交替配对**计算，报告记录源码、镜像、CPU 型号/拓扑、实际配额、资源节流及环境指纹；不把不同 run 的绝对延迟变化直接当作优化收益，也不推断线上最大容量。

每个正式 run 只启动一次待测环境。先确认当前机器的短时发压验证通过、业务表/Redis/提交日志为空，再在同一实例上进行固定预热和正式测量。每个预热/正式点使用新用户、新活动，发压前直接核对该点的初始库存、积分、订单与 Redis 数据；测后继续核对提交与守恒关系。每轮排空后才继续，不将未完成工作带到下一轮。

不再在正式 run 中预造整场规模的数据、进行额外低速探测再销毁重建。完整造数、低速业务路径、生成器完整形状及人为过载恢复被迁移到独立 **Experiment tooling regression** 工作流；相关源码或配置变更时执行，也可手动执行。只改报告展示不触发完整工具回归。回归结果不参与收益计算，也不能代替当前机器上的发压验证。

每次仍在实际选定的发压 CPU 上，以 2 CPU / 2 GiB / 6400 VU 验证 600 RPS、9 秒响应延迟、12 秒注入窗口的替身流量（之后等待响应排空）。证据绑定当前机器、Actions job、实验、CPU 集合和源码；旧 run 不能授权本次测量。依赖与 BuildKit 层可以缓存，业务数据、容器卷及验证结果不能缓存。构建 worker 在业务启动前停止。

## 判定与证据

- **completed**：所有正式点发压与数据核对有效。服务 SLO 未达标、无提升或负提升仍是正常实验结果。
- **inconclusive**：最终热身块不健康、有效配对或样本不足。不生成完整收益结论，不作为服务失败边界。
- **failed**：构建/运行出错、观测中断、正式点发压无效、事务压力证据不完整、数据不一致、无法排空、容器重启/OOM 等，立即停止后续点并保留具体原因与诊断；这不等于服务容量失败。

计划请求数必须完全发出，k6 VU 不足警告始终令该点无效。注入时间 p99 延迟上限 100ms；尾部最多允许计划数的 0.01%（最低 1 条）延后不超过 20ms，实际时间戳与容忍记录全部保留。其他时钟、窗口或调度异常不被掩盖。

Redis 主结论是相同负载下有效购买延迟与成功率变化；SQL 减少只能解释机制。按时成功要求响应成功且 ≤500ms、订单提交 ≤5s，以所有有效购买请求为分母；超时后实际提交不算按时成功。正文将响应延迟与错误数一起展示，逐笔证据仍保留所有响应及成功响应的延迟，防止快速网络失败被误读成优化。SQL 来自业务 mapper 调用计数，不是 MySQL 所有 SQL；事务尝试不等于事务提交。Kafka 的 PENDING 是受理而非完成，不能与同步 PAID 返回耗时计算收益。最终完成以订单、积分、库存及提交日志关联核对；超时响应后实际提交仍计入完成，并单独保留接口异常。Kafka 不设置 500ms 受理或 5s 完成目标，也不以这些阈值判定 SLO。HTTP 超时和最长 120 秒排空只是运行保护，不是业务达标期限；未排空的点不可继续污染后续对照。

Kafka 主指标为**覆盖基线、突发、低流量恢复及排空全窗口**的下单事务开始速率峰值与并发峰值。实验模块在下单作用域内、已获取数据库连接且事务有效的首条 MyBatis 调用处计入事务，在数据库提交或回滚后优先退出（先于其他提交证据回调，避免日志落盘被计为数据库处理）；多个 mapper 调用及参与外层事务不重复计数，重试的新事务仍计入压力。该口径不包含等待连接的时间，也不是 MySQL 实际 SQL 总量；不会以方法入口尝试数或订单提交速度替代。使用固定墙钟 1 秒桶，首尾不足 1 秒不外推，事件更新并发峰值，不以低频采样冒充精确峰值。

准备阶段的预请求完成并确认空闲后，通过仅存在于实验应用的鉴权接口开启新的事务窗口，同时清空计数、峰值和时间桶。窗口标识在测前、测后必须相同，测前必须为空；活动不匹配或事务未结束时拒绝重置。该流程也用于 Kafka 预热，使统计错误在正式实验前暴露。

每点 backend-after.json 保存完整事务桶及核对计数，database-timeline.csv 用于绘图。pressure-samples.json 保存连接等待和 Kafka committed-offset lag 的实际采样时刻，缺样不补零；lag 可能包含正在处理但尚未提交 offset 的消息。事务桶活动标识、总数、并发守恒及边界核验失败时不生成削峰比较，已完成的订单证据仍保留。完成 p50/p95/p99 只覆盖已提交的突发订单，必须同时展示突发最终完成率；最大未完成数由逐笔到达/提交时间计算，恢复时间覆盖突发批次最后一单。降低峰值可能只是放慢消费，必须与完成量及等待代价一起解读。

三组完整有效配对且样本充足才输出收益。延迟降幅逐对计算 `(前−后)/前×100%`；成功率变化使用百分点。展示每轮指标和配对差值的中位数、最小/最大值，允许负值；不把多轮 p99 平均成总体 p99。

每个 run 上传：

- `performance-html`：下载并打开 `index.html`，包含所选实验、环境、部分失败证据。
- `performance-evidence`：`suite.json`、`startup.json`、`generator-check/`、`timings.json`、诊断，以及 `<experiment>/<run-id>/experiment.json`、`manifest.json`、每点 `result.json` / `timeline.csv` / `requests.jsonl` / `commits.jsonl` 等。

GitHub Pages 分别保留两个实验最近一次完整正式报告，失败记录不会覆盖它们。旧静态报告只作为归档，不被新实验读取。

开发检查及校验说明见 [VALIDATION.md](VALIDATION.md)。

## 用于简历的表述

只有正式实验的实测值可以填入：“在共享两个逻辑 CPU / 2 GiB 被测部署预算、X RPS、90% 重复购买流量下，Redis 过滤使有效购买响应 p99 从 A 降至 B ms（三轮配对中位数），按时成功率由 C% 变为 D%。”Kafka 表述为：“在固定资源、600 RPS 突发下，下单事务并发峰值从 X 降至 Y、事务开始速率峰值从 A 降至 B 次/秒，突发订单最终完成率为 C%，完成 p99 为 T ms，积压在 Z 秒消化。”所有数字必须来自新的同次运行证据；不保证 Kafka 更优，不把响应语义变化或单纯提交变慢解释为削峰收益。保留每轮范围，收益为零或负值也照实展示；这些结论不等于最大容量或线上收益。

发压预算按固定最高 600 RPS、最长 10 秒 HTTP 超时配置：600 × 10 = 6000 个等待名额，再留 400 个余量，固定 6400 VU。短验证使用 9 秒响应延迟，不保证任意机器在所有故障下都能按时发压；实际请求数与时间戳仍须逐点核验。Nginx 共 16384 连接位（客户端和上游均占位），Tomcat 8192 连接，相关容器 nofile 32768；本地、生产、压测共享这些入口设置，业务线程数和数据库池不变。k6 固定 `GOMAXPROCS=2`，发压端使用与待测端不重叠的两个逻辑 CPU。在四 vCPU runner 上不再另外保留一个逻辑 CPU；宿主任务仍共享机器，并不独占物理核。

`checks` 仅显示配置与测试检查状态。报告函数默认不写 Actions summary；performance 的报告 CLI 显式传入 `--summary` 才写入所选实验结果。失败响应保留 k6 错误码、HTTP 状态、连接/阻塞时间；每阶段 `nginx-error.log` 在注入前开始跟随采集，避免访问日志轮转丢失早期错误。

## 报告与重生成

Redis 与 Kafka 共用图表组件，但各自声明方案名称和指标。Redis 展示有效购买 p95/p99、重复拒绝 p99；Kafka 展示事务速率及并发峰值，另展示突发完成 p50/p95/p99、最终完成率、最大未完成数和突发批次恢复时间。所有配对点图展示全部轮次；中位数不隐藏某一轮退化。方案列使用真实名称，配对差值先逐轮计算再汇总，可能不等于两列中位数相减。

Kafka 时间线默认第 1 轮，可切换到其他轮；所有轮次与方案使用相同坐标尺度。速率和积压分图，图上方用带线型的图例标注；实线与虚线使重合曲线仍可辨认。速率图同时显示请求到达、事务开始、订单提交；并发图显示事务并发及采样的连接等待；积压图显示未完成订单和采样的 Kafka lag，两者不可等同。恢复时间从突发结束算到突发批次全部完成，早于突发结束则为 0，缺失证据或未完成则显示 —。该值与停止全部注入后的排空时间不同。

成功报告只显示数据质量摘要。预热 JSON、容器终态、完整配置、原始采样留在证据包，异常会在正文明确显示。环境和源码链接仍可追溯。详细数据与统计口径直接展开；不设置实验结论、SQL 与事务或方法与适用范围章节。`timings.json` 记录构建/生成器/启动/测量各阶段耗时；预热及正式测量耗时还分别记录在 warmup.json 与 manifest.json。

已有证据解压后可直接重生成，不重新发压：

```bash
python3 scripts/experiments/lib/html_report.py --reports /path/to/extracted-evidence --output /path/to/new-html
```

重生成保留原 Actions run、实验源码 commit 和测量时间，并另记报告生成器 SHA-256。旧数据缺少突发恢复时间时，只读原 evidence.sqlite 按同一口径补算；原始 JSON/SQLite 不改写。不修改旧实验的协议、负载或配对结果。旧证据没有事务采集时明确显示“未采集”，不能回填或推算削峰收益；历史 5 秒达标和 PAID/PENDING 响应比较不再呈现在新版 Kafka 页面。

优化前最新 Redis/Kafka performance job 分别约 18分10秒/16分57秒。新流程的目标是先减少重复验证约 2～3 分钟，缓存命中时再缩短构建；不同机器、缓存命中和排空情况会影响实际耗时，不能把目标当实测结果。
