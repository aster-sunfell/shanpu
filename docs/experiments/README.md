# Redis 过滤与 Kafka 削峰实验

在 GitHub Actions 的 **Performance experiments → Run workflow** 中选择一个实验。每个 run 只启动所选实验，独立生成证据和 HTML 报告；push 不自动发压。需要两个实验时分别发起两个 run。

| 实验 | 对照 | 固定流量 | 重复 | 主指标 |
|---|---|---|---|---|
| `redis-filtering` | A 数据库同步 / B Redis 过滤后同步 | 200 RPS，60 秒；90% 已购重复、10% 有效购买 | 每路径 3 次，AB / BA / AB | 每千请求业务 SQL 调用数、同步事务尝试次数 |
| `kafka-burst` | B Redis 同步 / C Kafka 异步 | 100 RPS × 20 秒 → 400 RPS × 10 秒 → 100 RPS × 30 秒；全部有效购买 | 每路径 3 次，BC / CB / BC | 突发请求 500ms 内受理量、5s 内完成量 |

两项实验的正式注入时间均为 6 分钟。另有镜像构建、生成器校验、数据预检与重置、每路径 10 秒低速热身、数据准备和排空。排空最长 120 秒，确认无待完成订单、无 Kafka lag、无活跃事务后提前结束。不能保证整个 workflow 6 分钟结束。

不再执行容量搜索、阶梯、短探路、自动升降档或历史扫描，也不需要先测同步容量才能运行 Kafka 实验。默认负载来自已有观测并固化于 `scripts/experiments/lib/protocol.py`；一次实验内不根据结果改负载。改配置后需新建 run，不能与旧配置直接合并比较。

## 环境与公平性

本地开发依赖容器按需启动，前后端可手动启动。生产和压测待测端完整容器化并共享业务配置与配额，服务 `unless-stopped`；发压任务 `restart: no`。待测端总预算 2 vCPU / 2 GiB，发压端另配 1 vCPU / 1 GiB，固定 400 VU，不动态扩池。

两个端绑定同一 GitHub-hosted VM 的不同 CPU 集合，仍共享磁盘、缓存、内核与宿主机。GitHub Actions 每次分配的 CPU 型号、宿主争用可能变化。因此收益用**本次 run 内同负载的交替配对**计算，报告记录源码、镜像、CPU 型号/拓扑、实际配额、资源节流及环境指纹；不把不同 run 的绝对延迟变化直接当作优化收益，也不推断线上最大容量。

启动前只按所选实验的全部请求数加 20% 验证数据规模，只验证对应两条业务路径，再清空独立压测环境。正式点使用独立新用户与活动，积分、库存充足。预检及热身不参与收益比较。

## 判定与证据

- **completed**：所有正式点发压与数据核对有效。服务 SLO 未达标、无提升或负提升仍是正常实验结果。
- **inconclusive**：存在发压无效点。保留全部逐笔证据，确认排空和业务一致性后继续剩余固定对照；不生成完整收益结论，不作为服务失败边界。
- **failed**：构建/运行出错、观测中断、数据不一致、无法排空、容器重启/OOM 等，停止后续点并保留诊断。

计划请求数必须完全发出，k6 VU 不足警告始终令该点无效。注入时间 p99 延迟上限 100ms；尾部最多允许计划数的 0.01%（最低 1 条）延后不超过 20ms，实际时间戳与容忍记录全部保留。其他时钟、窗口或调度异常不被掩盖。

Redis 分别展示有效请求与重复拒绝延迟、错误及完成情况。SQL 来自业务 mapper 调用计数，不是 MySQL 所有 SQL；事务尝试不等于事务提交。Kafka 的 PENDING 是受理而非完成，最终完成以订单、积分、库存及提交日志关联核对；主指标只取突发段请求，另展示全程逐秒到达/完成、待完成峰值和排空时间。未排空的点不可继续污染后续对照。

三组完整有效配对且样本充足才输出收益。展示每轮指标和配对差值的中位数、最小/最大值，允许负值；不把多轮 p99 平均成总体 p99。

每个 run 上传：

- `load-recovery-check`：真实 k6 固定流量与过载分类校验，替身 HTTP 服务，不是业务性能证据。
- `performance-html`：下载并打开 `index.html`，包含所选实验、环境、部分失败证据。
- `performance-evidence`：`suite.json`、预检、诊断，以及 `<experiment>/<run-id>/experiment.json`、`manifest.json`、每点 `result.json` / `timeline.csv` / `requests.jsonl` / `commits.jsonl` 等。

GitHub Pages 分别保留两个实验最近一次完整正式报告，失败记录不会覆盖它们。旧静态报告只作为归档，不被新实验读取。

开发检查及校验说明见 [VALIDATION.md](VALIDATION.md)。
