# Redis 过滤与 Kafka 削峰实验

在 GitHub Actions 的 **Performance experiments → Run workflow** 中选择一个实验。每个 run 只启动所选实验，独立生成证据和 HTML 报告；push 不自动发压。需要两个实验时分别发起两个 run。

| 实验 | 对照 | 固定流量 | 重复 | 主指标 |
|---|---|---|---|---|
| `redis-filtering` | A 数据库同步 / B Redis 过滤后同步 | 600 RPS，60 秒；90% 已购重复、10% 有效购买 | 每路径 3 次，AB / BA / AB | 有效购买响应 p95/p99、按时成功率、最终完成率及错误率 |
| `kafka-burst` | B Redis 同步 / C Kafka 异步 | 100 RPS × 20 秒 → 600 RPS× 10 秒 → 100 RPS × 30 秒；全部有效购买 | 每路径 3 次，BC / CB / BC | 突发请求 500ms 内受理率、5s 内完成率、受理延迟；最终完成率与积压代价 |

两项实验的正式注入时间均为 6 分钟。另有镜像构建、生成器校验、数据预检与重置、每路径固定 90 秒热身、数据准备和排空。排空最长 120 秒，确认无待完成订单、无 Kafka lag、无活跃事务后提前结束。不能保证整个 workflow 6 分钟结束。

工作流只选择实验，不再提供 calibration，也不进行容量搜索或读取历史来选择负载。Redis 固定 600 RPS，Kafka 固定 600 RPS 突发段，在同一个 run 内完成三轮交替对照。修改负载需要提交配置并新建 run，不能与旧配置合并计算收益。

每条路径固定热身三块：100 RPS × 30 秒、200 RPS × 30 秒、200 RPS × 30 秒，顺序同样交替。短窗口 p95 和 CPU 波动仅作诊断，不决定是否延长热身或取消测量。前两块出现已知发压不足或响应失败时，仅在订单、积分、库存与提交证据核对通过且确认排空后继续。任一路径最后一块输入无效或响应异常，则标记 inconclusive，不开始正式对照。数据不一致、未完成订单或未知执行错误仍立即中止。

## 环境与公平性

本地开发依赖容器按需启动，前后端可手动启动。生产和压测待测端完整容器化并共享业务配置与资源设置，服务 `unless-stopped`；发压任务 `restart: no`。六个待测服务绑定同一组两个逻辑 CPU，取消服务级 CPU 配额和权重调整，空闲 CPU 时间可供其他服务使用；后端 JVM 可见处理器为 2。内存上限仍分别为 backend 512、MySQL 384、Redis 96、Kafka 384、frontend 192、Nginx 64 MiB，共 1632 MiB，另计宿主预算 416 MiB（不是硬预留）。发压端另配 1 vCPU / 2 GiB，固定 1200 VU，不动态扩池。启动和观测时验证 Docker 设置以及实际 cgroup 的 cpu.max / cpuset.cpus.effective。

两个端绑定同一 GitHub-hosted VM 的不同 CPU 集合，按拓扑避免跨端使用同一物理核的 SMT 线程；仍共享磁盘、缓存、内核与宿主机。两个逻辑 CPU 不保证等于两个物理核，cpuset 也不代表独占或宿主保留。GitHub Actions 每次分配的 CPU 型号、宿主争用可能变化。因此收益用**本次 run 内同负载的交替配对**计算，报告记录源码、镜像、CPU 型号/拓扑、实际配额、资源节流及环境指纹；不把不同 run 的绝对延迟变化直接当作优化收益，也不推断线上最大容量。

启动前只按所选实验的全部请求数与固定热身请求数之和加 20% 验证数据规模，只验证对应两条业务路径，再清空独立压测环境。正式点使用独立新用户与活动，积分、库存充足。预检及热身不参与收益比较。

## 判定与证据

- **completed**：所有正式点发压与数据核对有效。服务 SLO 未达标、无提升或负提升仍是正常实验结果。
- **inconclusive**：最终热身块不健康、时间预算不足或存在发压无效点。保留全部逐笔证据，确认排空和业务一致性后继续剩余固定对照；不生成完整收益结论，不作为服务失败边界。
- **failed**：构建/运行出错、观测中断、数据不一致、无法排空、容器重启/OOM 等，停止后续点并保留诊断。

计划请求数必须完全发出，k6 VU 不足警告始终令该点无效。注入时间 p99 延迟上限 100ms；尾部最多允许计划数的 0.01%（最低 1 条）延后不超过 20ms，实际时间戳与容忍记录全部保留。其他时钟、窗口或调度异常不被掩盖。

Redis 主结论是相同负载下有效购买延迟与成功率变化；SQL 减少只能解释机制。按时成功要求响应成功且 ≤500ms、订单提交 ≤5s，以所有有效购买请求为分母；超时后实际提交不算按时成功。分别展示所有响应与成功响应的延迟，防止快速网络失败把 p99 压低。SQL 来自业务 mapper 调用计数，不是 MySQL 所有 SQL；事务尝试不等于事务提交。Kafka 的 PENDING 是受理而非完成，最终完成以订单、积分、库存及提交日志关联核对；主指标只取突发段请求，另展示全程逐秒到达/完成、待完成峰值和排空时间。未排空的点不可继续污染后续对照。

三组完整有效配对且样本充足才输出收益。延迟降幅逐对计算 `(前−后)/前×100%`；成功率变化使用百分点。展示每轮指标和配对差值的中位数、最小/最大值，允许负值；不把多轮 p99 平均成总体 p99。

每个 run 上传：

- `load-recovery-check`：真实 k6 固定流量与过载分类校验，替身 HTTP 服务，不是业务性能证据。
- `performance-html`：下载并打开 `index.html`，包含所选实验、环境、部分失败证据。
- `performance-evidence`：`suite.json`、预检、诊断，以及 `<experiment>/<run-id>/experiment.json`、`manifest.json`、每点 `result.json` / `timeline.csv` / `requests.jsonl` / `commits.jsonl` 等。

GitHub Pages 分别保留两个实验最近一次完整正式报告，失败记录不会覆盖它们。旧静态报告只作为归档，不被新实验读取。

开发检查及校验说明见 [VALIDATION.md](VALIDATION.md)。

## 用于简历的表述

只有正式实验的实测值可以填入：“在共享两个逻辑 CPU / 2 GiB 被测部署预算、X RPS、90% 重复购买流量下，Redis 过滤使有效购买响应 p99 从 A 降至 B ms（三轮配对中位数），按时成功率由 C% 变为 D%。”Kafka 则同时陈述突发受理改善、5 秒内完成比例、最终完成比例、待完成峰值及排空时间，不能把响应改善写成订单吞吐提升。保留每轮范围，收益为零或负值也照实展示；这些结论不等于最大容量或线上收益。

发压预算按 800 RPS、1 秒响应延迟验证，1200 VU 留有余量；这不保证 10 秒超时下仍可维持 800 RPS。若服务变慢超出已验证范围，输入无效点只诊断，不生成收益。Nginx 共 4096 连接位（客户端和上游均占位），Tomcat 2048 连接，相关容器 nofile 8192。k6 固定 `GOMAXPROCS=1` 与其单 CPU 配额一致，避免按宿主 CPU 数调度。

`checks (unit tests)` 仅显示单元测试状态。报告函数默认不写 Actions summary；performance 的报告 CLI 显式传入 `--summary` 才写入所选实验结果。失败响应保留 k6 错误码、HTTP 状态、连接/阻塞时间；每阶段 `nginx-error.log` 在注入前开始跟随采集，避免访问日志轮转丢失早期错误。
