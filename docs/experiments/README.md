# GitHub Actions 性能实验

压测仅在 GitHub 托管 Linux runner 执行，在同一台临时虚拟机中运行后端、前端、Nginx、MySQL、Redis、Kafka 和独立的 Python/k6 发压容器。无需开发者本机运行服务，也无需在仓库配置数据库密码或 SSH 密钥 secrets。

待测端完整继承 `deploy/compose.2c2g.yml` 的生产部署；生产与待测服务使用 `restart: unless-stopped` 自动恢复，本地开发覆盖为 `restart: "no"`。发压容器不自动重启，防止重复实验。测量中的服务退出或重启仍使结果无效，自动恢复不能掩盖失败。完整启动方式与允许差异见 [部署说明](../DEPLOYMENT.md)。

后端与生产共用 Dockerfile 运行时、JVM 参数和 `2c2g` 应用配置：Tomcat 32 线程、256 个连接、64 个连接排队位、5 秒 keep-alive，数据库池最多 8 个连接。业务请求统一经过 Nginx；前端启动并计入资源预算，本轮不施加浏览器负载。

指标每秒原子写入 `/evidence/metrics.json`，提交日志写入同一专属卷，发压端以只读方式读取。观测不经业务 HTTP 连接，避免 200 VU 占满连接时指标超时；准备和结束阶段等待新快照，过期、实例不符或提交日志末尾不完整仍判为无效并保留现场。具体异常写入 `measurement-error.json` 和 HTML，最后快照保留在 diagnostics。实验启用提交/SQL 观测，并关闭补偿、超时处理、对账和定时预热；这些差异明确写入报告，结论限定于此实验条件。

实验设计和结论门槛见 [PLAN.md](PLAN.md)，迁移范围见 [GITHUB_ACTIONS_MIGRATION_PLAN.md](GITHUB_ACTIONS_MIGRATION_PLAN.md)，实现验证状态见 [VALIDATION.md](VALIDATION.md)。

## 触发实验

压测仅通过 `workflow_dispatch` 手动启动，平时向 main 或其他分支推送、提交 PR、创建标签和归档报告都不会自动发压。

需要压测时，打开 [Actions → Performance experiments](https://github.com/aster-sunfell/shanpu/actions/workflows/performance.yml)，点击 **Run workflow**，选择 **main** 和实验组 `full` / `redis` / `kafka`，再点击 **Run workflow**。每次点击先执行真实环境预检，通过并重建干净环境后才启动选定的实验，结束后自动发布 HTML；预检失败同样保留诊断并生成报告。仅允许 main 执行；选择其他分支时所有 job 跳过。

验证最新修正时请新建一次 Run workflow，不要在旧失败运行中点击 Re-run jobs；旧运行的重试沿用旧提交及其工作流配置。

运行进度见 [Actions → Performance experiments](https://github.com/aster-sunfell/shanpu/actions/workflows/performance.yml)。构建和测量串行进行，同一 main 分支的运行使用并发组排队，不取消正在进行的实验。

| 固定配置 | 值 | 用途 |
|---|---|---|
| experiment | full / redis / kafka | 默认 full；也可只验证一组，避免重复另一组 |
| A/B 固定起点 | 500 RPS | 根据已有观测固定配置，不扫描历史报告 |
| B/C 固定起点 | 300 RPS | 根据已有观测固定配置，不导入旧容量基线 |
| seconds | 60 | 正式容量点最低注入秒数，低速档按样本目标延长，单点最多 600 秒 |
| repeats | 3 | 正式测量至少三轮 |
| vus | 200 | 容量与突发统一预分配并固定 200 个 VU；不在测量中动态扩容 |
| refine_steps | 4 | 每条路径的有效通过/失败区间最多细化四轮 |
| probe_seconds / probe_steps | 20 秒 / 每路径最多 8 点 | 短时探路；只选候选，不计容量 |
| expand_steps | 2 | 仅显式 `--rates` 完整阶梯模式使用 |
| search_minutes | 30 | 每组总搜索预算，包含探路、正式确认、造数及核对 |
| publish | 自动 | 完成后发布已有 HTML，包括明确标记的中断或失败报告 |

默认固定起点定义在 `scripts/experiments/lib/protocol.py`：A/B 500 RPS，B/C 300 RPS。该配置根据运行 39557663264 确定，执行时不访问历史报告。先从固定起点进行每点 20 秒的 validation 探路：通过则升压 25%，未找到通过点则降压 20%，存在上下候选时做中点缩小，每路径最多 8 点。随后只对候选通过点和有效失败点做本次正式确认；若短时通过点在正式窗口失败，则在本次机器上补测更低候选。两条路径按轮次交错执行。

容量与突发继续统一使用固定 200 VU，发压端仍为 1 vCPU / 512 MiB，不在测量中动态扩容。VU 耗尽、计划请求缺失或注入延迟超限的点仍无效，不能作为服务容量失败上界。默认搜索只在提交证据、库存/积分/订单核对、排空和额外空闲检查都通过时，才保留无效点的磁盘证据、释放已核对点的临时热数据并继续其他路径；该路径仅报告正式测得的下限或另行确认更低点。未知发压错误、k6 非零退出、数据/证据错误、未完成受理、OOM 或重启仍停止整组。显式完整阶梯、预检和突发保持原有的发压错误中止行为。

窗口末尾迟到也属于无效注入；在窗口终点、计划时刻、时钟和业务证据均一致时，默认搜索允许排空后降档，不能将该点用于证明 SLO 通过或失败上界。窗口终点不一致、窗口开始前发出、计划时刻越界、比计划提前超过 50 ms、非数值时间戳及实际时钟跳变继续中止。原有窗口末尾 1 ms 精度容差与 p99 注入延迟 100 ms 要求不变。每点 `injection-timing.json` 和 `result.json.injectionTiming` 保存分类数量、最大偏差及至多五个请求示例；控制台和 HTML 诊断也展示异常，包括中止前未完成搜索登记的探路点。

短探路结果单独保存在 `probes/`，均标记 `phase=probe`、`scope=validation`，不计正式容量、样本量或配对收益。正式候选仍至少三轮、每轮 60 秒、每路径每档累计至少 1000 个有效样本。两条路径都有短时通过点时，先在较低候选上交错确认共同档位，随后只补较高候选及失败候选；通常需要 12～15 个正式测点。通过/失败区间过宽时最多补四轮正式细化；必要时补齐共同通过档位缺少的对照轮次。不存在明确边界时只输出下限，不能把探路或发压受限当作正式失败上界。

B/C 突发仅引用本 job 刚确认的正式 B 基线，要求区间宽度不超过 10%（最低 1 RPS），VU、超时、排空、环境与源码指纹匹配。预算不足或基线不合格时跳过突发；旧机器和旧运行的结果都不直接复用。

预算或探路轮数耗尽、机器在起点表现较弱、发压受限、非单调或未找到正式失败上界时，保留有效观测并将整组标为 `inconclusive`；各路径的原因见报告诊断。正式结果由本次机器重新确认，固定起点仅决定从哪里寻找。可用 `--rates` 显式切回原有的完整阶梯模式；普通运行无需设置该参数。修改后提交到 main，再手动新建工作流，push 不自动发压。

迁移期间已通过短时 smoke 验证 A/B、B/C 容量和突发的执行、证据关联及业务核对。验证报告标记 validation，不输出性能提升结论；当前工作流在 main 上手动选择 full 或单组实验。

## 正式测量前的真实环境预检

三个 job 保持为 checks、performance、publish。checks 标记为 unit tests，只验证工具逻辑；真实预检位于 performance 中，使用正式镜像、同一 runner 和原有资源配额，构建只执行一次。

镜像构建完成后、业务服务启动前，先运行 `scripts/experiments/checks/k6_recovery.py`：在无外网的 1 CPU / 512 MiB / 128 PID 容器中，用真实 k6 0.50.0、200 VU、生产发压脚本、证据分析和搜索代码验证 VU 耗尽、末尾迟到以及两者同时出现后的降档和另一条路径继续。HTTP 端为可控排队服务，库存/订单快照由其测试账本提供；短窗口和简化轮次只用于工具回归，不代表真实业务容量。该检查有意延迟尾部请求，并在单独的 VU 场景提前停止最后 100 ms 请求以隔离边界迟到。日志、逐笔记录和检查结果保留为独立的 `load-recovery-check` artifact；检查失败会在耗时的造数和正式压测之前阻断流程。

1. 读取实际 MySQL 版本和内存配置，检查 cgroup 资源。MySQL 启动时要求至少 64 MiB 工作集估算余量，造数及短时请求阶段要求至少 32 MiB；OOM、重启、计数缺失或余量不足即停止。工作集估算为 memory.current 减 inactive_file，原始占用、内存类型与压力事件同时保留；这不是实际可分配内存保证，也不把正常文件缓存直接当作泄漏。
2. 根据选定实验组的固定起点正式测量块准备 1.2 倍用户规模。默认 full 为 288000 个起点请求、345600 个造数用户，每批最多 30000；仅 redis 为 216000 个用户，仅 kafka 为 129600 个用户。交替走 A/B 准备流程，核对混合比例、订单、流水、余额、库存与已购集合，批间释放 Redis 热数据但保留 DB 历史。通过记录绑定起点、搜索策略和 200 VU。该规模只覆盖起点测量块加余量，不保证覆盖完整搜索；不为旧低档阶梯重复准备百万级数据。
3. 在已有大规模数据上，对 A/B/C 分别先执行 10 秒低速预热，再用独立用户和活动执行 10 秒低速验证。速率为 `min(5, 最低初始 RPS)`，默认 5 RPS；即使选择 1 RPS，每阶段仍包含混合流量中的有效购买请求。两阶段复用原 k6、证据关联和排空核对；发压无效、业务错误或未完成受理仍会阻止正式运行，但不以正式 SLO 或最高档 RPS 作为预检通过条件。预检日志和 evidence 保存阶段、路径、速率、计划/实际请求数和错误，失败点同样保留。
4. 预检通过后先归档日志与提交证据，再销毁专属容器和数据卷，复用镜像重建。必须确认新实例、镜像与配额一致、六张业务表为空、Redis 为空、提交日志为空。随后签发绑定本次 run/attempt/job、代码、参数和新实例的一次性通过记录，正式执行入口缺少或不匹配时拒绝测量。

造数与短时请求设 12 分钟内部预算，包含保护排空与环境重建的 workflow 步骤上限为 20 分钟，时间仍计入既有全程截止。预算不保证大规模数据一定能准备完成；超时或内存检查失败仍阻断正式测量。失败报告标记 validation，并保留运行失败原因。预检详情及环境重建核验不进入 HTML，原始证据位于 `preflight/<run>-<attempt>-preflight/`；通过记录只在 runner 临时目录内。

预检覆盖配置的起点正式测量块及低速运行能力，不覆盖所有自适应候选、突发和长时间数据累积。正式搜索继续监控宿主/容器内存、OOM、重启和磁盘余量；准备或核对失败仍中止。预检通过后重建空库与进程，预检状态不作为正式结果；宿主缓存和内核仍由同一个 runner 共享。

## 资源条件

固定使用 `ubuntu-24.04`，要求至少四个可用 vCPU。两个 vCPU 分配给被测服务、一个给发压端，其余用于宿主；两端集合互斥，优先将系统报告的 SMT 兄弟留在同组，记录实际分配。vCPU 不代表物理核独占。

| 服务 | CPU 硬上限 | 内存硬上限 |
|---|---:|---:|
| backend | 0.75 | 512 MiB |
| MySQL | 0.5 | 384 MiB |
| Redis | 0.1 | 96 MiB |
| Kafka | 0.4 | 384 MiB |
| frontend | 0.15 | 192 MiB |
| Nginx | 0.1 | 64 MiB |
| 发压端 | 1 | 512 MiB |

被测容器内存合计 1632 MiB，416 MiB 为宿主余量预算，不是对宿主内存的硬预留。不能将容器配额解释为独立 2 核 / 2 GiB 服务器。环境不足时失败，不降低预算继续。前端和网关加入预算后，后端/Kafka 配额也随之调整，旧配置结果必须重测。

运行时镜像固定 digest。checks 及执行前比较展开后的生产、待测和本地中间件配置，Docker inspect 核验 CPU、内存、swap、PID、CPU 集合和重启策略；后端快照记录实际 Tomcat、数据库池和 JVM 参数。配置指纹保存在 `target.configurationAlignment`，修改配置后禁止沿用旧容量基线。

MySQL 固定为 8.0.46，在 384 MiB 配额内关闭未使用的 Performance Schema，并限制线程缓存和内部临时表内存；InnoDB 缓冲池仍为 128 MiB。每阶段开始前读取并核验实际数据库变量，保存到 `mysql-settings.json`，HTML 中可展开“MySQL 实际配置与版本”。配置不匹配时停止；配置变化会改变基线指纹。这是被测环境调整，结果限定于新配置，不能与旧配置的测量点混合得出收益结论。详见 [PLAN.md](PLAN.md)。

构建和测量不重叠。启动及发压前要求可用内存至少 3 GiB；监控到低于 1 GiB、证据盘不足 1 GiB、容器 OOM/重启、时钟异常或观测缺失时中止并保存已有证据。低于 512 MiB 时优先停止专属容器。

job 上限 180 分钟；正式测量内部最多 135 分钟、每组容量搜索默认 30 分钟，包含构建准备的全程截止仍为 160 分钟。较早的截止优先，执行器提前停止启动新档位，为排空和归档留出余量；硬截止仍由看门狗执行。完整实验耗时取决于阶梯、样本窗口、细化和机器状态，不能保证等于先前环境的一小时。

## 查看 HTML 与原始证据

每次运行结束后，在该 Actions 运行页面下载：

- `performance-html`：HTML 报告与精简索引，保留 30 天；解压后直接打开 `index.html`，无需联网加载图表库。
- `performance-evidence`：结构化报告、逐笔请求/提交/快照、SQLite、CSV、JVM/DB/Kafka 和宿主采样、服务日志，保留 14 天。

artifact 下载可能需要登录 GitHub。HTML 显示实验范围、commit、环境、输入达标情况、分类 p99、容量区间、按时完成订单、积压曲线和无效原因。容量实验中的有效 SLO 失败点用于构成上界，不能与发压无效或样本不足混为一谈。执行中断也会尽量生成部分报告；平台强制终止可能影响收尾。

正式报告采用图表优先的布局：首屏比较摘要、方案说明、Redis 过滤的延迟与容量、Kafka 异步化的稳定容量与突发收益，随后展示实验环境。图例使用“数据库同步”“Redis 同步”“Kafka 异步”，字母只用于对应原始记录。目录随正文滚动高亮，支持锚点定位；积压曲线可切换实际测得的档位和轮次，并使用共享的真实数量 / 时间坐标。方法说明、逐点结果、容器 / MySQL 配置和异常位于折叠详情中。

两组实验各自显示“本实验达标条件（SLO）”，解释响应、完成和错误率的含义，并从该实验的实际 policy 读取阈值；缺失时显示“未采集”，容量和突发的策略不同时分别列出。Redis 过滤实验区分有效购买与重复拒绝；Kafka 实验区分 PAID / PENDING 响应和数据库最终完成，并说明突发超标不等于测量无效。图内只保留“响应目标”等短标注。延迟结论注明代表压力是双方均达标的最高已测共同档位；展示名称统一为“降幅”，按同一轮先比较再汇总的计算方式保持不变。

收益数字来自协议产出的合格配对和容量边界，不从图形反推结论。首屏延迟选择双方合格的最高共同档位，突发选择最低的完整合格档位，不挑最大收益；阶段中断、样本 / 配对不足、非单调容量或 validation 不生成相应增幅。完整阶段的结论可在后续阶段失败时保留，但不会将整场标为成功。新增的 `result.json.burst` 及 `burstExtra*OnTime` 配对字段只统计 `burst:` 场景请求；原有整场计数继续保留。旧证据缺少突发段字段时，页面明确标为“整场（含低负载段）”，不与突发段口径混合。

“实验环境”以可读字段展示本次采集的 CPU 型号、Runner 可用逻辑 CPU 与可见内存、被测端 CPU/内存预算、被测端与发压端 CPU 集合，以及 Runner 镜像和内核版本。CPU 型号中的核心数不代表实验分配的核心数，Runner 总内存也不等于被测容器配额；缺失字段标为“未采集”。环境信息位于测量结果之后，不展示原始环境 JSON。

入口仍为 `scripts/experiments/lib/html_report.py`，布局、SVG 图表和证据读取分别位于 `report_layout.py`、`report_charts.py`、`report_data.py`。`html_report.css` 和 `html_report.js` 在生成时内联进 HTML，下载后无需额外资源或联网；`.local` 中的预览脚本不参与正式报告生成。

凭证和用户 token 仅位于 runner 临时目录，未挂入公开站点。Pages 仅发布渲染后的 HTML 和精简索引；原始数据留在 evidence artifact，不写回源码分支。每个测量点核对后释放 Redis 热数据，DB 数据在本 job 中累积；归档后销毁本次容器和数据卷。

数据准备阶段按本批已验证的用户 ID 直接写入订单和积分流水，造数事务每批最多覆盖 100 个用户，单批内检查影响行数并原子更新订单、流水、余额和库存。这不改变 90% 重复请求的测量流量比例，也不改变 RPS、时长、轮次或服务配额。

每点的 `preparation.json` 记录准备步骤、用户索引范围和累计耗时；失败日志显示具体步骤及该批事务耗时。每阶段的 `containers-final.json` 保存退出后、清理前的容器状态（包含 MySQL 的退出码、OOM 标志和重启次数），仅导出必要字段，并在 Actions 日志打印状态摘要。HTML 同时展示未完成的数据准备和结束时容器状态。断连后不自动重放造数事务，提交结果不明时保留证据并停止。

## 一次性配置 Pages 和仓库 Website

1. 仓库 Settings → Actions → General：允许本工作流使用的 GitHub 官方 actions。权限按 job 显式声明，不要求把所有 workflow 的默认权限改成全仓库读写。
2. Settings → Pages → Build and deployment → Source 选择 **GitHub Actions**。
3. 仓库 Code 页右侧 About 的设置中，Website 填写 `https://aster-sunfell.github.io/shanpu/`。
4. 在 Actions → Performance experiments → Run workflow 中选择 main，手动启动正式实验。确认 `publish` job 成功并打开 Website。

发布 job 使用 `contents: write` 保存纯静态报告的 `report-history` 分支，使用 `pages: write` 和 `id-token: write` 部署 Pages；压测 job 仅有 `contents: read`。无需提供个人访问令牌。首次配置仍需仓库管理员在 GitHub 完成。

网站展示运行历史，保留最近 30 次，以及最近一次完整正式实验。验证或失败报告不会覆盖该完整报告入口。workflow 的发布过程串行执行，合并完整历史站点后再部署，避免覆盖旧报告。
