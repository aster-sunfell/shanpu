# GitHub Actions 压测迁移计划

日期：2026-10-20。状态：实施中，云端与发布验收待完成。

将现有压测改为 GitHub Actions 专用流程，在单个 GitHub 托管 runner 中运行被测系统、发压工具和结果分析。删除本地压测入口和兼容逻辑，保留现有实验方法、业务核对和原始证据分析。

## 1. 分支与工作目录

从当前提交创建 `refactor/github-actions-load-testing` 分支，使用独立 Git worktree 开发，保留原工作目录及正在运行的实验现场。

计划制定时，当前分支为 `main`，原始提交 `83fc56b` 在身份迁移后对应 `03ded58`，实施基于后者。工作区包含未提交的 `VALIDATION.md` 修改和 `redis-filtering` 压测结果；这些记录不带入迁移分支，也不因删除本地压测代码而删除原始现场。

## 2. 先验证 Actions 资源条件

先在真实 runner 上检查 Docker、CPU 拓扑、可用内存和磁盘，再开始完整迁移。

当前公开仓库标准 Ubuntu runner 为 4 vCPU / 16 GB，私有仓库为 2 vCPU / 8 GB。私有仓库标准 runner 不满足现有“被测端 2 CPU＋发压端 1 CPU”的预算。实施时核实仓库可见性和实际 runner 规格，不自动降低实验预算，也不自动更改仓库可见性或启用付费 runner。

CPU 隔离规则改为适用于虚拟机：两个 vCPU 给被测端，一个给发压端，剩余资源供宿主使用。两端逻辑 CPU 集合互斥，记录 SMT 关系和共享限制，明确结果使用的是 vCPU 配额，不宣称物理核独占。原有“三个不同物理核”检查需要重写，不能直接假定 Actions 满足。

被测端保留当前各服务 CPU 和内存硬上限；发压容器保留 1 CPU / 512 MiB 限制。资源不满足准入要求时明确失败。

参考：[GitHub 托管 runner 规格](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)。

## 3. 重构为 Actions 专用运行流程

新建压测 workflow，固定 Ubuntu 镜像版本，提供手动触发入口，支持选择：

- A/B 容量实验。
- B/C 容量与突发实验。
- 完整实验流程。
- 短时流程验证。

一个 job 内依次完成：

1. 检查环境和资源条件。
2. 拉取依赖、构建应用和镜像。
3. 启动并核验被测服务与发压容器。
4. 准备数据、预热并执行实验。
5. 停止注入、观察排空并核对数据。
6. 分析结果、生成报告并上传证据。
7. 停止服务并销毁临时环境。

构建和上传均安排在测量窗口之外。服务通过同一 runner 内的网络通信，不需要 VPN 或跨机器协调。

B/C 容量与突发必须在同一个 job、同一套服务环境里执行，直接引用刚测出的合格基线，避免临时 runner 销毁后环境身份失配。容量基线不合格时，不执行依赖该基线的突发实验。

## 4. 删除本地压测支持

| 删除或替换 | 迁移后的实现 |
|---|---|
| 本地 `sut.sh`、运行和清理入口 | Actions 内部执行脚本 |
| `same-host` / `separate-host` 部署选择 | 唯一的 Actions 单机部署 |
| Windows、WSL、PowerShell 检查 | Linux runner 监控 |
| 手动 CPU 绑定及持久化配置 | 每次自动探测、绑定和核验 |
| 跨机器配置、凭证复制、身份及时钟协调 | 同一 runner 自动初始化 |
| `.local/experiments` 工作目录约定 | Actions 临时目录与产物目录 |
| 跨运行保留环境、人工数据清理流程 | 每次全新环境，结束后销毁 |

同步删除对应测试和文档，不保留本地执行模式或兼容开关。Actions 内部脚本仅服务于云端生命周期管理。

保留并改造 Docker Compose、容器配额、Linux 资源监控和必要的时钟异常检测，这些仍是云端压测所需的基础设施。删除范围限定为压测模块，普通业务开发环境不受影响。

主要改造位置：

- `.github/workflows/`：新增 Actions 压测入口。
- `scripts/experiments/`：删除本地入口，重构生命周期、监控、参数及报告逻辑。
- `experiments/`：调整 Compose、Docker 构建和临时数据管理。
- `scripts/experiments/tests/`：删除本地兼容测试，补充迁移所需验证。
- `docs/experiments/`：重写操作说明、实验环境约定与验证记录。

## 5. 保留实验标准并重新建立基线

保留以下测量方法和判据：

- A/B 固定 10% 有效请求、90% 已购重复请求。
- B/C 的受理与最终完成语义，以及同一实测 Q_B 下的突发比较。
- 阶梯升压、容量区间细化、交错多轮和最低样本量。
- 分类延迟、错误率、完成时限、积压稳定性及现有 SLO。
- 订单、库存、积分与提交证据的逐笔核对。
- 实际发压速率、调度偏差、缺失请求和发压端资源检查。

报告协议升级，记录 commit、Actions run、runner 环境、镜像、配额和 CPU 分配。旧本地报告不能作为新环境的突发基线，性能结论限定在该 Actions 运行环境下。

明确区分实验正常完成、有效 SLO 失败、测量无效和样本不足。容量实验找到有效失败上界属于正常结果，不能简单使用“SLO 失败即整个 workflow 失败”的规则。短时验证不输出正式性能结论，也不能作为正式突发基线。

## 6. 超时与证据归档

job 超时暂设为 180 分钟，内部实验截止时间更短，为停止发压、排空和归档留出余量。当前普通 GitHub 托管 runner 的单个 job 上限为 6 小时；本机约一小时的实验迁移后仍需通过实际运行确认耗时。

每个测量点完成后更新结构化结果。报告进入 Job Summary；原始请求、提交证据、资源采样和服务日志压缩为 artifacts，并设置保留期限。规划磁盘用量，避免镜像、数据库和逐笔证据耗尽空间。

异常退出时尽量上传已有证据，再清理环境；平台强制终止或基础设施故障时不保证能完成收尾。凭证文件不进入日志和上传产物。

参考：[GitHub Actions 时长与存储限制](https://docs.github.com/en/actions/reference/limits)。

## 7. 分支验证与验收

依次执行：

1. 静态检查、必要单元测试和构建验证。
2. 真实 Actions 环境探测及短时流程验证。
3. 完整 A/B 正式容量实验。
4. 同一 job 内完成 B/C 正式容量与突发实验。
5. 检查失败处理、产物下载和文档中的执行步骤。

验收要求：

- 全程不依赖开发者本机服务、文件或凭证。
- 实际发压、样本量与数据核对满足既定要求。
- B/C 基线可以在同一次运行中用于突发实验。
- 失败可定位原因，已有证据可下载。
- 仓库中不再保留本地压测入口和使用说明。
- 普通业务构建和开发环境正常。

## 8. 交付物

- `refactor/github-actions-load-testing` 分支上的完整迁移。
- Actions 专用运行说明及更新后的实验环境约定。
- 真实 Actions 环境探测、短时验证和正式实验记录。

仅完成 workflow 或短时预跑不算迁移完成。需要跑完正式实验，检查结果与证据质量后，再评估是否达到预期；评估通过前保留原分支作为回退依据。

## 9. HTML 报告与 Website 入口

每次 Actions 运行生成可离线打开的 HTML 和原始证据 artifacts。main 手动运行可将 HTML 发布到 GitHub Pages，仓库 About 的 Website 指向 `https://aster-sunfell.github.io/shanpu/`。Pages 仅包含 HTML 和精简运行索引，使用独立报告历史分支保存最近 30 次及最近完整正式实验；验证、中断与失败均明确标记。

工作流内声明最小 job 权限，无需个人 token secrets。首次需要管理员启用 Pages 的 GitHub Actions 来源并设置 Website。迁移分支可先通过 push 自动完成 smoke 和 HTML 下载产物验证，再进行正式实验和在线报告验收。

## 10. main 合并后的触发策略

根据最终实施要求，工作流只监听 main 的 push，不保留手动、PR、标签或迁移分支触发。任何 main 新提交均运行完整正式 full 实验，结束后发布已有 HTML；report-history 的归档提交不触发压测。实验参数直接定义在 workflow 中。Pages 与 Website 已配置，合并后的第一次 main push 用于正式实验和线上报告验收。
